# ForgeSync 구현 성과와 의미

ForgeSync는 설비 데이터를 보기 좋게 꾸미는 데서 출발하지 않았다. 현장에서 보는 숫자를 믿을 수 있고,
문제가 생겼을 때 과거 상황을 다시 살펴볼 수 있으며, 데이터가 말하지 않은 사실을 시스템이 만들어 내지
않는 것이 먼저였다.

현재는 NIST Smart Manufacturing Systems Test Bed의 `Mazak01` 기록을 바탕으로 원본 보존, 데이터
변환, 과거 재생, 디지털 트윈, 가공 분석, 운영 알람과 데이터 품질 확인까지 하나의 흐름으로 연결돼 있다.
이 문서는 그 결과가 사업, 기술, 데이터 분석 측면에서 어떤 의미가 있는지 설명한다.

## 지금 무엇을 할 수 있나

ForgeSync는 세 가지 화면을 제공한다.

- 교대조 개요 `/`: 전체 관찰 구간의 가동 상태, 정지 구간, 가공 건수와 알람 흐름을 살핀다.
- 공장 보기 `/factory`: 선택한 시점의 설비 상태를 2D와 3D로 함께 보고 과거 가공을 비교한다.
- 데이터 품질 `/data-quality`: 원본 해석, 의미 변환, 수신 상태와 분석 가능 범위를 따로 확인한다.

운영자는 개요에서 긴 정지나 알람 시점을 찾고, 그 시점으로 이동해 설비 상태와 가공 기록을 자세히 볼 수
있다. 과거 시점으로 이동하면 2D, 3D, 알람과 분석 화면이 같은 재생 위치를 사용한다.

## 사업적으로 어떤 의미가 있나

### 현상을 설명할 수 있는 운영 화면

화면에 나온 값은 원본의 어느 기록에서 왔는지 추적할 수 있다. 실제 관찰, 계산한 값, 화면을 위한 모형도
서로 구분한다. 운영자가 숫자를 보는 데서 끝나지 않고 그 숫자의 근거까지 확인할 수 있는 구조다.

### 같은 문제를 다시 살펴볼 수 있는 환경

과거 기록을 1배, 10배, 100배로 재생하고 일시정지하거나 원하는 시점으로 이동할 수 있다. 장애 조사나
운영 검토 때 기억과 설명에만 의존하지 않고, 같은 데이터와 같은 순서로 당시 상황을 다시 볼 수 있다.

### 잘못된 판단을 줄이는 경계

원천 `Condition`(설비가 보낸 상태 신호)을 모두 업무 알람으로 만들지 않는다. 검토한 규칙에 맞는 항목만
알람으로 승격하고, 열림·작업자 확인·해제 상태를 관리한다. 부품 카운터 증가를 생산 완료로, 부하 변화를
공구 마모로, 품질 데이터가 없는 상황을 종합 설비 효율(OEE)로 바꾸지도 않는다.

기능이 적어서 숫자를 만들지 않은 것이 아니다. 근거 없는 숫자가 실제 의사결정에 사용되는 위험을 막기
위한 제품 원칙이다.

코드: [알람 생명주기와 승격 규칙](../apps/factory-api/src/main/java/com/forgesync/factoryapi/alarm/),
[알람 화면](../apps/factory-web/src/features/alarm/),
[알람 계약](../contracts/alarm/v1/)

### 다음 설비와 데이터로 넓힐 수 있는 기반

원천 데이터, 공통 의미, 현재 상태, 화면 표현을 분리했다. 새로운 설비를 연결할 때 기존 화면과 분석을
모두 다시 만드는 대신, 설비별 의미 매핑과 화면 연결 지점을 명시적으로 추가할 수 있다.

## 기술적으로 무엇이 달라졌나

### 원본부터 화면까지 이어지는 데이터 길

```text
원본 파일
→ 원본 레코드
→ 공통 의미를 가진 관찰
→ 안전한 전달과 저장
→ 설비의 현재 상태
→ 운영 지표와 2D·3D 화면
```

원본 파일은 받은 내용 그대로 보관하며 크기와 SHA-256 체크섬을 남긴다. 변환한 데이터는 원본 위치와
매핑 버전을 함께 보관한다. 나중에 규칙이 바뀌어도 과거 결과를 덮어쓰지 않고 새로운 처리 결과를 만든다.

코드: [원천 수집과 의미 변환](../apps/edge-gateway/src/forgesync_edge/ingestion/),
[Mazak01 의미 매핑](../config/mappings/nist-mazak01-observation-v2.json),
[공통 관찰 계약](../contracts/observation-envelope/v2/)

### 중복과 늦은 데이터에 안전한 재생

메시지는 여러 번 도착할 수 있다는 전제로 처리한다. 같은 재생 세션의 같은 사건은 데이터베이스 업무에
한 번만 반영한다. 늦게 도착한 과거 관찰은 이력에는 남지만 현재 설비 상태를 뒤로 돌리지 않는다.
원천이 기록한 시각과 ForgeSync가 다시 발행한 시각도 섞지 않는다.

코드: [재생 엔진](../apps/edge-gateway/src/forgesync_edge/replay/),
[재생 제어 API](../apps/factory-api/src/main/java/com/forgesync/factoryapi/replay/),
[재생 계약](../contracts/replay/v1/)

### 2D와 3D가 공유하는 하나의 디지털 트윈

2D와 3D는 서로 상태를 만들지 않고 같은 디지털 트윈을 읽는다. 3D는 서버 응답을 직접 해석하지 않고
화면 전용 상태로 한 번 변환한다. 그래픽 초기화나 모델 표시가 실패해도 2D 핵심 정보는 계속 사용할 수
있다. 데이터가 오래됐거나 설비가 멈추면 3D 움직임도 멈춘다.

코드: [설비 상태와 순서 규칙](../apps/factory-api/src/main/java/com/forgesync/factoryapi/equipmenttwin/),
[웹 디지털 트윈](../apps/factory-web/src/features/twin/),
[3D 상태 연결](../apps/factory-web/src/features/factory3d/)

### 기능별로 나눈 책임

재생, 설비 상태, 가공 분석, 알람, 데이터 품질과 생산 문맥을 서로 다른 책임 영역으로 나눴다. 한 기능의
내부 데이터베이스 구조를 다른 기능이 직접 사용하는 대신 공개된 계약과 식별자로 연결한다. 이 구조는
규칙을 바꿀 때 영향을 받는 범위를 줄이고, 각 의미를 독립적으로 검증할 수 있게 한다.

## 데이터 분석으로 무엇을 알 수 있나

### 데이터가 실제로 얼마나 쓰였는지 알 수 있다

고정한 Mazak01 원본에는 115,991개 레코드가 있다. 문법 해석 실패는 없었고, 이 가운데 101,693개를
공통 의미로 변환했다. 현재 의미 변환률은 87.67%다. 지원하지 않는 항목과 뜻을 확인하지 못한 항목도
버리지 않고 따로 집계한다.

데이터 품질은 하나의 점수로 합치지 않는다. 원본 해석, 의미 변환, 재생 수신, 중복, 순서, 최신성과
가공 분석 범위를 각각 보여 준다. 기대 수집 주기를 모르면 완전성을 100%로 표시하지 않고 측정할 수
없다고 밝힌다.

근거: [의미 변환 보고서](./data/mappings/nist-mazak01-observation-v2/mapping-report.md),
[데이터 품질 결정](./adr/ADR-056-layered-data-quality-without-overall-score.md)

코드: [데이터 품질 계산](../apps/factory-api/src/main/java/com/forgesync/factoryapi/dataquality/),
[데이터 품질 화면](../apps/factory-web/src/features/data-quality/),
[데이터 품질 계약](../contracts/data-quality/v1/)

### 관찰 기록에서 가공 흐름을 재구성했다

실행 상태 변화를 이용해 가공 시작과 종료 구간을 찾았다. 완료된 가공은 시간, 주축 속도, 부하와 이송
특징을 같은 규칙으로 요약한다. 비교할 때는 같은 설비와 프로그램의 이전 가공만 기준으로 사용하며,
표본이 부족하면 차이 숫자를 만들지 않는다.

이 결과는 관찰에서 재구성한 `가공 런`이다. 작업 지시나 확정된 생산 실적은 아니다.

코드: [가공 분석 규칙](../apps/factory-api/src/main/java/com/forgesync/factoryapi/processanalytics/),
[가공 분석 화면](../apps/factory-web/src/features/process-analytics/)

### 가동과 정지를 서로 다른 근거로 볼 수 있다

실행 상태를 시간 구간으로 바꿔 ACTIVE, READY, STOPPED, INTERRUPTED, UNKNOWN에 머문 시간을 계산했다.
상태 구간으로 계산한 값과 기계 누적 카운터로 계산한 값은 근거가 다르므로 차이를 숨기지 않는다.

긴 정지 구간에는 같은 시간에 관찰된 비상 정지, 제어 모드 변화와 Condition을 함께 보여 준다. 다만 함께
관찰됐다는 이유만으로 정지 원인이라고 단정하지 않는다.

코드: [가동 상태와 정지 분석](../apps/factory-api/src/main/java/com/forgesync/factoryapi/equipmenttwin/domain/),
[교대조 개요](../apps/factory-web/src/features/dashboard/)

### 생산 문맥과 생산 실적을 구분했다

프로그램, 하위 프로그램, 가공 런과 부품 카운터를 같은 시간축에 놓았다. 프로그램별 가공 건수와 시간은
볼 수 있지만, 시간상 겹친 관계만으로 생산 완료·양품·불량을 확정하지 않는다. 원천에 생산 결과가 없기
때문이다.

코드: [생산 문맥](../apps/factory-api/src/main/java/com/forgesync/factoryapi/production/),
[생산 문맥 화면](../apps/factory-web/src/features/production/),

### 공구 부하 변화는 채널별로만 비교한다

같은 프로그램과 공구에서 관찰된 부하를 B, C, C2, X, Y, Z 채널별로 분리했다. 실제 재생 위치에서
40개 그룹이 확인됐지만, 현재 그룹들은 유효한 비교 표본이 부족해 숫자 추세를 표시하지 않는다.

이는 공구 마모량이나 잔여 수명 예측이 아니라 관찰된 부하 변화다. 실제 마모 정답 데이터가 생기기 전에는
두 의미를 연결하지 않는다.

코드: [공구 부하 추세 규칙](../apps/factory-api/src/main/java/com/forgesync/factoryapi/processanalytics/),
[공구 부하 화면](../apps/factory-web/src/features/tool-load-trend/),

|---|---|
| 평가 가능한 가공 94건 중 92건을 차이가 있다고 분류했다. | 작은 통계 차이를 곧바로 전체 이상으로 보면 안 됐다. 가공시간을 주 기준으로 다시 정하고 채널별 차이는 보조 근거로 남겼다. 정상 범위는 2건에서 76건으로 바뀌었다. |
| 가공 122건을 한 타임라인에 그대로 놓으니 막대가 겹치고 목록이 지나치게 길어졌다. | 원래 시간축은 유지하되 밀집 구간을 요약하고, 필터와 점진적 목록 표시를 추가했다. 많은 데이터에서도 흐름과 개별 가공을 함께 찾을 수 있게 됐다. |
| 3D 화면 높이를 반복 측정하면서 캔버스와 문서 높이가 계속 늘어났다. | 측정값이 실제로 달라졌을 때만 화면을 갱신하도록 바꿨다. 실제 브라우저에서 문서와 캔버스 높이가 안정적으로 유지되는 것을 확인했다. |
| 재생이 정상 종료됐는데 오래된 데이터 경고가 고장처럼 보였다. | 데이터 최신성과 재생 상태는 함께 설명해야 했다. 선택 시점, 마지막 재생 데이터, 실제 지연을 서로 다른 문구로 표시했다. |

## 아직 말할 수 없는 것

- 실제 CNC, PLC 또는 Safety PLC를 제어하지 않는다.
- 3D 공장 배치와 기계 모형은 실제 공장을 측량한 결과가 아니다.
- 3D 경로는 실제 절삭 흔적이나 소재 제거 결과가 아니다.
- 공구 번호는 관찰했지만 공구 종류와 형상은 확인하지 못했다.
- 부품 카운터와 가공 런만으로 생산 완료, 양품과 불량을 확정하지 않는다.
- 품질 원천이 없으므로 종합 OEE를 계산하지 않는다.
- 부하 추세를 실제 공구 마모량이나 잔여 수명으로 사용하지 않는다.
- 실제 다설비와 장시간 운영 성능은 별도 검증이 필요하다.

## 근거와 검증

각 주장과 확인 상태는 [검증 장부](./verification-ledger.md)에 기록돼 있다. 중요한 데이터 의미와 설계
결정은 [설계 결정 기록](./adr/)에서 확인할 수 있다. 실제 PostgreSQL, MQTT, API, Web과 Chromium을
연결한 전체 흐름 검증도 포함한다.

테스트와 실행 코드의 시작점은 다음과 같다.

- [전체 검증 명령](../scripts/verify)
- [데이터베이스 통합 검증](../scripts/verify-database)
- [브라우저 전체 흐름 검증](../scripts/verify-e2e)
- [웹 브라우저 시나리오](../apps/factory-web/tests/e2e/)
- [공통 계약 검증 자료](../tests/fixtures/)

ForgeSync가 지금까지 만든 가장 중요한 결과는 숫자가 많은 화면이 아니다. 원본에서 운영 화면까지 데이터의
길을 설명할 수 있고, 같은 과거를 다시 확인할 수 있으며, 근거가 없는 결론은 만들지 않는 운영 기반이다.
