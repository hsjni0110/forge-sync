# ForgeSync 도메인 용어

이 문서는 ForgeSync에서 같은 개념을 같은 이름과 의미로 사용하기 위한 공통 언어를 정의한다.
제품, 코드, API, 스키마, 테스트, 문서와 UI가 서로 다른 뜻으로 같은 이름을 사용하지 않게 하는
것이 목적이다.

## 1. 이 문서를 읽는 순서

독자와 목적에 따라 필요한 부분부터 읽는다.

- 제품과 화면의 개념을 이해하려면 **2. 핵심 용어**를 먼저 읽는다.
- 특정 기능의 책임과 데이터 의미를 설계하려면 **3~9절의 Context별 상세 용어**를 읽는다.
- 메시지 처리, 계약 또는 코드 이름을 구현하려면 **10~12절의 개발·계약 용어**를 읽는다.

코드와 public contract에서는 표의 **코드·계약 명칭**을 사용한다. 한글 UI와 사용자 문서에서는
**한국어 표준명**을 우선 사용하고, 개발자 문서에서는 첫 사용 시
`한국어 표준명(코드·계약 명칭)`으로 병기할 수 있다.

정의된 개념을 코드나 계약에서 임의의 동의어로 바꾸지 않는다. 외부 규격의 이름은 Adapter에서
ForgeSync 용어로 번역한다. 일반 설명에서는 자연스러운 한국어를 사용할 수 있지만, 서로 다른
도메인 개념을 같은 이름으로 축약해서는 안 된다.

새 용어에는 소유 Bounded Context, 정의와 구분해야 할 인접 개념을 함께 기록한다. 데이터 의미나
Context 소유권을 바꾸는 용어 변경은 단순 rename으로 처리하지 않고 ADR로 결정한다.

## 2. 핵심 용어

아래 용어는 제품, UI, 도메인 대화에서 먼저 이해해야 하는 공통 개념이다.

| 한국어 표준명 | 코드·계약 명칭 | 쉽게 풀어 쓴 정의 | 예시 또는 구분 |
|---|---|---|---|
| ForgeSync | ForgeSync | 제조 데이터의 의미와 출처를 보존하면서 설비 상태와 생산 운영 정보를 하나의 운영 모델로 연결하는 플랫폼 | MES 전체나 실제 설비 제어 시스템은 아니다. |
| 설비 | Machine | ForgeSync가 식별하고 상태를 추적하는 개별 제조 설비 | `Mazak01`; MTConnect `Device`는 외부 규격을 가리킬 때만 사용한다. |
| 설비 식별자 | Machine Identity | 시간이나 연동 시스템이 달라져도 같은 설비를 가리키는 안정적인 식별자 | 화면 표시명이나 MQTT topic을 식별자로 사용하지 않는다. |
| 디지털 트윈 | Digital Twin | 식별자, 최신 관찰값, 설비 상태, 생산 맥락, 출처와 최신성을 모은 권위 있는 운영 모델 | 3D Model은 Digital Twin을 보여 주는 방법 중 하나다. |
| 관찰 | Observation | 특정 시각에 원천에서 관찰한 측정값, 상태 변화 또는 설비 condition | 주축 속도 1,200 rpm, 실행 상태 변경, `FAULT` condition |
| 설비 상태 | Equipment State | 여러 유효한 관찰을 해석해 구성한 설비의 현재 운영 상태 | 연결, 실행, 건강 및 정비 상태를 포함할 수 있다. 단순한 원천값 목록이 아니다. |
| 최신성 | Freshness | 데이터가 ForgeSync에 마지막으로 반영된 뒤 얼마나 지났는지 나타내는 상태 | `FRESH`, `LAGGING`, `STALE`; 과거 원천 시각만으로 판단하지 않는다. |
| 재생 세션 | Replay Session | 일정 범위의 과거 데이터를 일시정지, 배속, 재개하며 재생하는 식별 가능한 생명주기 | 원본 사건 시각은 바꾸지 않고 발행 시점만 조절한다. |
| 생산 요청 | Production Request | 제품, 계획 수량, 납기와 우선순위를 표현한 생산 요청 | 하나 이상의 작업 지시로 나눌 수 있다. |
| 작업 지시 | Work Order | 생산 요청을 실제로 수행하기 위해 나눈 생산 실행 단위 | 일반적인 `job`, `task`를 코드 이름으로 사용하지 않는다. |
| 공정 실행 | Operation Execution | 특정 설비에 배정된 생산 공정이 실제로 실행되는 생명주기 | 계획된 라우팅 공정과 구분한다. |
| 생산 실적 | Production Result | 완료·양품·불량 수량과 실제 소요 시간을 포함한 확정된 생산 결과 | 설비의 part count 측정값만으로 자동 확정하지 않는다. |
| 설비 상태 보고 | Condition | 원천이 보고한 `NORMAL`, `WARNING`, `FAULT`, `UNAVAILABLE` 등의 상태 관찰 | 운영자가 처리하는 알람과 다르다. |
| 알람 | Alarm | 명시적인 알람 규칙에 따라 생성되고 확인과 해결 상태를 추적하는 운영 알림 | 설비 상태 보고나 분석 조언을 자동으로 알람이라 부르지 않는다. |
| 정비 요청 | Maintenance Request | 설비 점검이나 수리를 요청하고 배정부터 완료까지 추적하는 독립된 작업 | 알람과 연결할 수 있지만 알람의 하위 상태는 아니다. |
| 분석 조언 | Advisory | 분석 기능이 설비 상태를 해석해 제공하는 조언 | 조언만으로 실제 설비 장애나 제어 명령을 만들지 않는다. |
| 출처와 계보 | Provenance | 값이 어디서 왔고 어떤 변환을 거쳤는지 보여 주는 정보 | 서로 다른 출처를 합치면 각 필드의 출처와 계보를 유지한다. |

제품이 답해야 하는 핵심 흐름은 다음과 같다.

```text
원천의 Observation
  → 현재 Equipment State와 Freshness
  → Production / Alarm / Maintenance
  → 2D·3D 화면
```

3D 화면은 Digital Twin을 표현할 뿐 권위 있는 상태를 직접 변경하거나 소유하지 않는다.

## 3. Bounded Context와 소유권

Bounded Context는 용어와 규칙이 한 가지 의미를 갖는 책임 경계다. 같은 개념을 여러 Context가
서로 다르게 소유하지 않도록 다음 경계를 사용한다.

| Context | 한글 설명 | 소유하는 핵심 용어 |
|---|---|---|
| Source Acquisition | 원천 수집 | Source Artifact, Raw Record, Source Manifest, Source Profile |
| Ingestion | 관찰 수신과 수락 | Observation Envelope, Semantic Mapping, Inbox |
| Replay | 과거 데이터 재생 | Replay Session, Replay Clock, Replay Sequence |
| Equipment Twin | 설비의 권위 있는 현재 상태 | Machine Identity, Equipment State, Twin Version, Freshness |
| Production | 생산 요청부터 결과까지의 실행 | Production Request, Work Order, Routing, Operation Execution, Production Result |
| Alarm | 규칙으로 생성된 운영 알림 | Alarm, Alarm Rule, Acknowledgement |
| Maintenance | 독립적인 정비 작업 생명주기 | Maintenance Request, Assignment |
| Intelligence | 설비 상태에 대한 분석과 조언 | Feature Schema, Model Metadata, Advisory |
| Presentation | 2D·3D 화면 모델 | View Model, Machine Visual State, Scene State |

## 4. Source Acquisition과 데이터 계층

### 4.1 원천 수집 용어

| 한국어 표준명 | 코드·계약 명칭 | 정의 | 구분 규칙 |
|---|---|---|---|
| 원천 묶음 | Source Set | 같은 목적과 version으로 함께 수집하고 검증해야 하는 원천 파일 묶음 | 개별 Source Artifact와 혼용하지 않는다. |
| 원천 잠금 명세 | Source Lock | Source Set의 URI, commit, 크기, checksum과 사용 조건을 고정한 재현 가능한 입력 명세 | Source Manifest는 실제 수집 결과이고 Source Lock은 기대하는 입력이다. |
| 원천 원본 | Source Artifact | L0. 외부에서 받은 byte를 변경하지 않고 manifest와 함께 보존한 원본 | `raw data`, `raw file`은 일반 설명에만 사용한다. |
| 원천 원본 명세 | Source Manifest | Source Artifact의 출처, 크기, SHA-256, 수집 시각, 사용 조건과 수집 도구 version을 기록한 부속 명세 | Source Lock이나 Acquisition Receipt와 다르다. |
| 수집 기록 | Acquisition Receipt | 한 번의 수집 시도와 성공·실패, 처리한 Artifact를 남긴 실행 기록 | Artifact 내용 자체의 identity가 아니다. |
| 체크섬 | Checksum | byte가 기대한 원본과 같은지 검증하는 해시 | 현재 SHA-256을 사용하며 파일명이나 크기만으로 동일성을 판단하지 않는다. |
| 원천 레코드 | Raw Record | L1. 원본 안에서 레코드 경계만 식별한 결과 | 아직 ForgeSync의 표준 의미를 부여하지 않으며 Observation이나 업무 Event라 부르지 않는다. |
| 원천 위치 | Source Locator | Raw Record가 Source Artifact의 어느 위치에서 왔는지 나타내는 줄, byte offset, path 또는 sequence | 파싱에 실패해도 원본 위치를 버리지 않는다. |
| 원천 카탈로그 | Source Catalog | `Devices.xml` 등에서 파생한 원천 metadata 목록 | Canonical schema가 아니며 원본 XML을 대체하지 않는다. |
| 데이터 항목 | Data Item | MTConnect Source Catalog가 선언한 개별 데이터 항목 | Canonical metric과 자동으로 같은 의미라고 보지 않는다. 코드에서는 `DataItem`을 사용한다. |
| 파싱 상태 | Parse Status | Raw Record의 문법 해석 결과 | 현재 값은 `PARSED`, `UNKNOWN_DATA_ITEM`, `AMBIGUOUS_DATA_ITEM`, `INVALID`다. mapping 결과와 섞지 않는다. |
| 처리 실행 | Processing Run | 고정된 입력과 parser·mapping version으로 수행한 한 번의 파생 처리 | 원본을 수정하지 않고 새로운 `processingRunId`의 결과를 만든다. |
| 원천 프로필 | Source Profile | 원천의 구조, 품질, 기간과 미해석 항목을 사람이 검토하고 기계가 읽을 수 있게 만든 재생성 가능한 결과 | 원본이 아니며 같은 입력과 도구 version으로 다시 만들 수 있다. |

### 4.2 데이터 계층

```text
L0 Source Artifact
  ↓ 레코드 경계 식별과 catalog 생성
L1 Raw Record / Source Catalog
  ↓ Semantic Mapping
L2 Canonical Observation
  ↓ Projection
L3 Operational Projection
```

뒤 단계는 앞 단계의 파일이나 레코드를 덮어쓰지 않는다. `raw`, `canonical`, `projection`은 데이터
성숙도의 서로 다른 단계이며 교환 가능한 이름이 아니다.

## 5. Observation과 Ingestion

| 한국어 표준명 | 코드·계약 명칭 | 정의 | 구분 규칙 |
|---|---|---|---|
| 표준 관찰 | Canonical Observation | L2. 원천 형식을 ForgeSync의 표준 의미와 단위로 변환한 Observation | 원천에 없는 의미, 단위, sequence 또는 timestamp를 만들어 내지 않는다. |
| 관찰 봉투 | Observation Envelope | 하나의 Canonical Observation에 identity, 순서, 시간과 provenance를 함께 담아 전달하는 versioned contract | Raw Record의 외부 형식을 그대로 노출하지 않는다. |
| 연속값 관찰 | Sample Observation | 연속적으로 측정되는 수치형 값 | 주축 속도, 온도, 부하 |
| 상태 변화 관찰 | Event Observation | 값이 바뀐 사실을 나타내는 이산형 관찰 | 실행 상태, 프로그램, part count; Domain Event와 다르다. |
| 상태 보고 관찰 | Condition Observation | 설비가 보고한 `NORMAL`, `WARNING`, `FAULT`, `UNAVAILABLE` 등의 Condition | Alarm Rule 없이 Alarm으로 변환하지 않는다. |
| 의미 매핑 | Semantic Mapping | Source Catalog를 기준으로 Raw Record를 Canonical Observation으로 변환하는 versioned 규칙 | 모르는 단위나 의미를 추측하지 않는다. |
| 매핑 버전 | Mapping Version | Semantic Mapping 규칙의 version | parser version이나 schema version과 다르다. |
| 미해석 데이터 항목 | Unknown Data Item | Source Catalog에 없거나 안전하게 mapping할 수 없는 Data Item | 버리거나 비슷한 metric으로 추측하지 않고 원본 위치와 함께 계수한다. |
| 의미 변환률 | Semantic Coverage | 문법 해석에 성공한 대상 중 catalog와 mapping에 성공한 비율 | 전체 데이터 정확도나 3D 표시율이 아니다. profile/runtime 중 어느 단계의 값인지 함께 밝힌다. |

`Sample Observation`, `Event Observation`, `Condition Observation`의 category는 원천 의미를
보존하며 서로 바꾸지 않는다.

## 6. Replay, 시간과 순서

| 한국어 표준명 | 코드·계약 명칭 | 정의 | 구분 규칙 |
|---|---|---|---|
| 재생 시계 | Replay Clock | Replay Session의 가상 시간과 배속을 제어하는 clock | 원천이 기록한 Source Observed At을 바꾸지 않는다. |
| 재생 순번 | Replay Sequence | 같은 Replay Session 안에서 Observation이 발행된 순서 | 원천에 없는 source sequence를 위조한 값이 아니다. |
| 원천 이벤트 키 | Source Event Key | 같은 원천 레코드를 다시 읽어도 같은 값이 나오는 안정적인 식별자 | 매 재처리마다 새 UUID를 부여하지 않으며 중복 수신 판별에 사용한다. |
| 원천 관찰 시각 | Source Observed At | 원천이 Observation이 발생했다고 기록한 시각 | 재생 발행·수신·projection 시각으로 덮어쓰지 않는다. |
| 재생 발행 시각 | Replay Published At | Replay가 Observation을 발행한 실제 시각 | Source Observed At과 다르다. |
| 수신 시각 | Ingested At | Ingestion 경계가 Observation을 수신한 실제 시각 | Projected At과 다르다. |
| 반영 시각 | Projected At | Observation이 Twin Projection에 반영된 실제 시각 | 원천의 사건 시각이 아니다. |

같은 Replay Session의 정렬 우선순위는
`replaySequence → sourceObservedAt → sourceEventKey`다. 늦게 도착한 과거 Observation은 이력에
저장할 수 있지만 현재 Twin을 이전 상태로 되돌리지 않는다.

Freshness는 최신 `projectedAt` 또는 계약에서 명시한 최신 수신 시각과 현재 wall clock의 차이로
판단한다. historical `sourceObservedAt`과 현재 시각을 비교해 live freshness를 계산하지 않는다.

## 7. Equipment Twin과 Presentation

| 한국어 표준명 | 코드·계약 명칭 | 정의 | 구분 규칙 |
|---|---|---|---|
| 조회 투영 | Projection | Domain Event나 Observation을 해석해 만든 재생성 가능한 조회용 상태 | 원본이나 권위 있는 상태의 원천이 아니다. |
| 운영 투영 | Operational Projection | L3. Canonical Observation으로부터 만든, 사람이 이해할 수 있는 현재 운영 상태 | 원본과 L2 Observation을 대체하지 않는다. |
| 최신 유효 관찰 | Latest Valid Observation | ordering과 validity 규칙을 통과해 현재 Projection에 사용하는 가장 최신의 Observation | 나중에 도착한 과거 Observation이 항상 latest가 되지는 않는다. |
| 트윈 버전 | Twin Version | Twin Projection의 변경 순서를 나타내는 단조 증가 version | source sequence나 Replay Sequence와 다르다. |
| 운영 트윈 조회 계약 | Operational Twin DTO | Equipment Twin이 외부에 제공하는 versioned 조회 contract | Domain Entity 자체를 직렬화한 것이 아니다. |
| 화면 모델 | View Model | UI가 표시하기 좋게 application 또는 Presentation 경계에서 구성한 조회 모델 | Domain Entity나 권위 있는 상태의 원천이 아니다. |
| 설비 시각 상태 | Machine Visual State | Operational Twin DTO를 2D·3D 표현에 필요한 최소 상태로 번역한 Presentation 모델 | 3D component가 backend DTO를 직접 해석하지 않는다. |
| 장면 상태 | Scene State | 선택, camera, view mode 등 3D 사용자 환경의 상태 | Machine의 권위 있는 운영 상태가 아니다. |

## 8. Production

| 한국어 표준명 | 코드·계약 명칭 | 정의 | 구분 규칙 |
|---|---|---|---|
| 라우팅 | Routing | Product를 만들기 위한 순서 있는 Routing Operation 목록 | 실행 중인 Operation Execution과 다르다. |
| 라우팅 공정 | Routing Operation | Routing에 포함된 계획 단계 | 특정 Machine에서 실행되는 생명주기가 아니다. |
| 설비 능력 | Machine Capability | Machine이 수행할 수 있는 process type 등의 능력 정보 | 현재 Equipment State와 다르다. |
| 텔레메트리 생산 수량 | Telemetry Part Count | 설비가 관찰값으로 보고한 생산 수량 | 업무적으로 확정한 Production Result와 다르다. |

생산 생명주기의 고정된 이름은 다음과 같다.

```text
Production Request → Work Order → Operation Execution → Production Result
```

## 9. Condition, Alarm, Maintenance와 Intelligence

| 한국어 표준명 | 코드·계약 명칭 | 정의 | 구분 규칙 |
|---|---|---|---|
| 알람 규칙 | Alarm Rule | Condition, Data Quality 또는 Advisory를 운영자가 조치할 Alarm으로 바꾸는 명시적 규칙 | 원천의 `FAULT`가 자동으로 Alarm이 되지는 않는다. |
| 알람 확인 | Acknowledgement | 운영자가 Alarm을 확인했음을 남기는 행위와 기록 | Alarm이 해결되었다는 뜻은 아니다. |
| 정비 담당 배정 | Assignment | Maintenance Request를 담당자나 담당 조직에 배정한 기록 | Maintenance Request 자체나 완료 상태와 다르다. |
| 특징 스키마 | Feature Schema | Intelligence가 입력으로 사용하는 feature의 이름, 타입, 단위와 version을 정의한 계약 | 원천 schema나 Observation schema와 다르다. |
| 모델 메타데이터 | Model Metadata | Intelligence model의 identity, version, 입력 계약과 provenance를 설명하는 정보 | 예측 결과인 Advisory와 다르다. |
| 장애 상태 | Fault | Condition Observation 또는 Equipment State의 건강 상태가 보고하는 장애 상태 | Alarm이나 Advisory와 같지 않다. |

생명주기는 다음과 같이 구분한다.

```text
Alarm:               OPEN → ACKNOWLEDGED → RESOLVED
Maintenance Request: REQUESTED → ASSIGNED → IN_PROGRESS → COMPLETED / CANCELLED
```

두 생명주기의 관계는 다음과 같다.

```text
Condition / Data Quality / Advisory
                ↓ 명시적인 Alarm Rule
              Alarm
                ↓ 선택적인 운영 절차
        Maintenance Request
```

Advisory의 수준은 `LOW`, `MEDIUM`, `HIGH`, `UNKNOWN`이다. `HIGH`라는 이유만으로 Machine을
`FAULT`로 바꾸거나 Alarm 또는 제어 command를 만들지 않는다.

## 10. Provenance, 근거 상태와 데이터 품질

| 한국어 표준명 | 코드·계약 명칭 | 정의 | 구분 규칙 |
|---|---|---|---|
| 근거 상태 | Evidence State | 중요한 사실이나 주장이 어떤 근거로 확인 또는 결정되었는지를 나타내는 상태 | 값의 데이터 출처인 Provenance와 다르다. |
| 데이터 품질 | Data Quality | validity, completeness, ordering, duplication, freshness와 semantic coverage로 관찰하는 데이터 상태 | 근거 없이 하나의 `qualityScore`로 축약하지 않는다. |
| 유효성 | Validity | 값과 구조가 선언된 schema와 도메인 규칙을 만족하는 정도 | 값이 존재하는지를 뜻하는 Completeness와 다르다. |
| 완전성 | Completeness | 계약상 필요한 값이나 레코드가 빠지지 않은 정도 | 값이 올바른지를 뜻하는 Validity와 다르다. |
| 순서 품질 | Ordering | Observation이 선언된 순서 규칙을 지키는지 나타내는 품질 항목 | 늦게 도착했다는 이유만으로 원본 이력을 버리지 않는다. |
| 중복 품질 | Duplication | 같은 identity를 가진 입력이 반복된 정도 | 중복 전달과 business side effect의 중복 반영은 별도로 관찰한다. |

Evidence State의 허용 값은 사용하는 문서와 versioned contract가 정의한다. 제품 결정 표시는 PRD의
`Evidence States`를 따르고, 외부 사실 검증 상태는 `docs/verification-ledger.md`의 상태 정의를
따른다. `PRIMARY`처럼 source의 선택 역할을 나타내는 표시는 Provenance나 검증 상태와 같은 뜻으로
사용하지 않는다.

## 11. 개발·계약 용어

이 절의 용어는 주로 개발자와 계약 작성자가 사용한다. 사용자 UI에 그대로 노출할 필요는 없다.

| 한국어 설명 | 코드·계약 명칭 | 정의 | 구분 규칙 |
|---|---|---|---|
| 수신 중복 방지 기록 | Inbox | `(replaySessionId, sourceEventKey)`를 유일 키로 사용해 중복 입력의 business side effect를 막는 기록 | message broker queue와 같은 뜻이 아니다. |
| 발행 대기 기록 | Outbox | 하나의 transaction에서 business state와 함께 저장하는 발행 대기 Domain Event | 모든 raw telemetry를 Outbox event로 만들지 않는다. |
| 도메인 사건 | Domain Event | `ALARM_CREATED`, `OPERATION_COMPLETED`처럼 도메인에서 이미 일어난 의미 있는 사실 | Event Observation이나 transport message와 다르다. |
| 최소 한 번 전달 | At-least-once Delivery | 같은 message가 한 번 이상 전달될 수 있는 MQTT QoS1의 전달 특성 | 중복이 없다는 뜻이 아니다. |
| 멱등 처리 | Idempotent Processing | 같은 identity의 입력을 반복 처리해도 business side effect가 한 번만 반영되는 성질 | message가 한 번만 도착했다는 뜻이 아니다. |
| 경계 내 사실상 한 번 처리 | Effectively-once Business Processing | 선언된 DB transaction 경계 안에서 중복 business side effect를 방지하는 보장 | global exactly-once라고 표현하지 않는다. |

## 12. 반드시 구분하는 표현

| 서로 다른 개념 | 이유 |
|---|---|
| `Source Artifact ≠ Raw Record` | Artifact는 원본 byte이고 Record는 그 안에서 식별한 레코드다. |
| `Raw Record ≠ Canonical Observation` | Raw Record에는 ForgeSync 표준 의미가 아직 부여되지 않았다. |
| `Event Observation ≠ Domain Event` | 하나는 설비 값의 관찰이고 다른 하나는 업무적으로 의미 있는 사실이다. |
| `Condition ≠ Alarm` | Alarm은 명시적인 업무 규칙이 적용된 운영 개체다. |
| `Advisory ≠ Fault` | AI 조언만으로 실제 설비 장애를 주장할 수 없다. |
| `Telemetry Part Count ≠ Production Result` | 설비 측정값은 생산 실적을 확정하는 business record가 아니다. |
| `Digital Twin ≠ 3D Model` | 3D는 Twin을 표현하는 방법 중 하나이며 권위 있는 상태가 아니다. |
| `Source Observed At ≠ Replay Published At ≠ Ingested At ≠ Projected At` | 사건, 발행, 수신, 반영 시각은 지연 측정과 재현을 위해 따로 보존한다. |
| `At-least-once ≠ Exactly-once` | MQTT QoS1은 중복 전달을 허용한다. |

## 14. 용어 변경 체크리스트

새 개념을 만들거나 이름을 바꾸기 전에 다음을 확인한다.

- 기존 용어로 표현할 수 없는 새로운 개념인가?
- 이 개념의 소유 Bounded Context가 하나로 명확한가?
- 식별자, 생명주기와 불변식이 기존 개념과 다른가?
- API, schema, event와 UI의 기존 이름과 충돌하지 않는가?
- 제품/UI 용어인가, Context 상세 용어인가, 개발·계약 용어인가?
- 용어집, 관련 계약, 테스트와 필요한 ADR을 함께 변경했는가?
